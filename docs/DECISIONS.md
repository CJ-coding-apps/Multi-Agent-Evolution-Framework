# Decisions

Design decisions for MAF, recorded so that contributors — human or agent — build on them rather than re-derive them. One entry per decision: what was decided, why, and what it implies. Entries are numbered for citation in pull requests ("implements D-03"). Status is *decided* unless marked otherwise; an entry is changed by a new entry that supersedes it, never by editing history.

Decided 2026-10-08 by the maintainer, following an independent audit of v0.2.0.

## Execution model

**D-01 · Governed in-process execution is the default for writer roles.** Every guarantee MAF makes — policy verdicts, secret redaction, attested tool calls, processor hooks — exists only on the in-process tier. A role that holds a write tool therefore runs in-process by default. The `cli` tier remains available as an explicit opt-in and prints a visible warning that the run is ungoverned. A writer role whose adapter cannot run in-process refuses to start rather than falling back silently; `--allow-ungoverned` is the override.

**D-02 · Escalate asks a human in the terminal; headless runs deny.** When stdin is a TTY, an `Escalate` verdict prompts for approval. When it is not (CI, scheduled runs), the call is refused and the request is written to `.maf/approvals/pending/<id>.json` for audit. Approval decisions are bound to a hash of the actual request and recorded in the attestation. GitHub pull-request review is not an approval channel in this release.

**D-03 · MAF never modifies the user's branch.** Every run creates a git worktree on a `maf/<runId>` branch and works there. On success MAF prints the merge command; it does not merge. On a gate failure the worktree is kept for inspection. `--no-worktree` runs in place and warns. Rollbacks (`git reset --hard`) are permitted only against the run's own worktree branch.

**D-04 · A node that did not finish did not succeed.** `budget_exhausted` (the node's own `maxTurns` or `tokenBudget`) is a failure with that reason. A DAG node may opt in to `allowPartial: true`. On the `cli` tier, an adapter result with `success: false` or empty output from a writer role fails the node, with the exit code and output tail in the error.

**D-05 · Provider failure is not node failure: fail over, then pause.** Provider errors are classified: transient (retry with backoff), quota or rate limit (fail over to the next entry in the role's `adapters: [primary, fallback, …]` chain, recorded in the attestation), authentication (fail). When the chain is exhausted the run enters `paused` with a checkpoint — DAG state, blackboard, worktree branch — and `maf resume <runId>` continues it, automatically after the provider's retry-after when known, otherwise manually.

**D-06 · Retries are for transport, never for verdicts.** A node is retried only on transport failures (timeout, non-zero exit with no output, network error), at most twice. A security-gate rejection or a policy refusal is terminal. The baseline commit for the security diff is captured once per node, not per attempt.

## Security gate and policy

**D-07 · The security gate reviews the whole diff or fails the node.** A diff above the configured size is a node failure, never a truncated review. `passed` is derived from finding severities alone; the reviewing model's own `passed` boolean is ignored. The gate applies to every role that holds a write tool, not to a role name.

**D-08 · Policy files are YAML, validated, and fail closed.** Policies load through `PolicyLoader` with schema validation (JSON remains valid YAML). A missing file warns and loads no rules. A file that does not parse refuses to run. Path globs match dotfiles (`minimatch` with `dot: true`).

**D-09 · Tool writes to `.git/**` and `.maf/**` are denied by default.** A coder commits through the gated `git.commit` tool, never by writing into `.git/`; a hook written there would execute outside every gate. MAF writes its own transcripts, attestations and harness files through its own code path, not the tool layer, so the rule costs the agent nothing. `.gitignore`, `.gitattributes` and a `.githooks/` directory live outside `.git/` and remain writable.

**D-10 · Child processes get the environment they need and nothing else.** Backend CLIs receive the full environment minus `MAF_*` variables. Tools (`grep`, `patch`, `test.run`) receive an allowlist (`PATH`, `HOME`, `LANG`, `TMPDIR`, plus a configurable passthrough). The signing key never reaches an agent-controlled process.

**D-11 · `test.run` executes project code and says so.** It is bounded — runner allowlist, arguments after `--`, process-group kill on timeout, a timeout ceiling, the minimal environment — and SECURITY.md states plainly that it runs the project's own tests, which the tester role may have written.

**D-12 · Model-supplied strings are never parsed as options.** `grep` passes the pattern as `-e <pattern> --`; `git.log` validates `n` as a positive safe integer; `git.reset` uses `--end-of-options`; the git helper sets `GIT_LITERAL_PATHSPECS=1`.

## Evidence

**D-13 · Attestations are in-toto Statements over canonical JSON.** The bundle is a real in-toto Statement signed (HMAC) over a canonical form so that a third party can reproduce the bytes. Refused tool calls are recorded. The bundle carries `keySource: "env" | "dev"`; running with the development key prints a loud warning and is never mistaken for a real signature.

**D-14 · Evaluation is offline, isolated and reproducible.** `goldens run --adapter scripted` runs without a model. A default harness and a baseline result are committed. Results record the corpus sha, the attempt count and the adapter. Each evaluation uses a temporary on-disk graph emptied before each attempt so past runs cannot leak into the prompt. The judge uses a different role or model than the agent when one is available and discloses when it does not.

**D-15 · The evolver only proposes edits that can take effect, and pays only after the gate.** Edits that cannot affect a role's configured tier are rejected at proposal time with the reason. Screening and structural checks run before any evaluation spend. The smoke test runs the target task. Sensitive edits are stored as candidates and shipped with `maf evolve approve <id>`.

**D-16 · The planner's failure recall matches the schema it queries.** Task and Failure nodes are written when a node fails; `CAUSED_FAILURE` is a `relation` value on `MemoryEdge`; the recall query is tested against a real Kùzu database.

## Components

**D-17 · The LCM context engine is built, not stubbed.** Summaries come from the run's adapter (model configurable, counted against the budget); both modes are implemented; the fresh tail is newest-first; compaction summarizes the entries it drops; ghost cues reach the injector; the `lcm` section of `config.yaml` is read. Until this ships, the README lists LCM as experimental.

**D-18 · Existing components are wired, not removed.** `ToolLoop`/`PatchTestCycle`/`CircuitBreaker`/`RollbackManager` become the opt-in `--strategy patch-test` coder strategy. `BlackboardSqlitePersistence`/`BlackboardValidator`/`FlushOnSnapshot` provide run persistence, which is the checkpoint D-05 relies on. `DagSynthesizer` backs `--plan-from <spec>`. `FailurePatternDetector` serves D-16. The LCM operators serve D-17. `SubgraphQuery`/`RunMerger` are consolidated with the duplicate methods on `MemoryGraph` into one implementation. Every wired component gets tests and a README status row.

**D-19 · `maf harness import` exists; `maf knowledge sync` does not.** The first is implemented (validate, copy, index). References to the second are removed.

**D-20 · Kùzu is pinned to 0.11.3, the final release, everywhere.** The Node binding moves from 0.7.1 to exactly 0.11.3 behind `maf graph export` / `maf graph import`; an old-format database is refused with instructions. The prebuilt binary must install on the maintainer's platforms with Node 22 before the bump lands; a source build is not an acceptable install path.

**D-21 · Toolchain floor: Node 22, pnpm 10.** `engines` declares Node ≥ 22. pnpm 10 with `onlyBuiltDependencies` for `kuzu` and `better-sqlite3`; lockfile v9. Native prerequisites are documented in the README.

## Process

**D-22 · Releases: 0.2.1, then 0.3.0, then 0.4.0.** 0.2.1 carries the correctness fixes and the documentation truth pass. 0.3.0 carries D-01 through D-03, D-08, D-13, D-14, D-16 and D-19. 0.4.0 carries D-05, D-15, D-17, D-18, D-20 and hardening.

**D-23 · The README describes shipped behaviour only.** A Status table (shipped / experimental / planned) is the first section after the summary. A claim appears as prose only when its row says shipped. The documentation pass runs last in each release so it matches what landed.

**D-24 · CI proves what the README demonstrates.** Every job has `timeout-minutes`. An end-to-end job runs `inprocess-demo` and the offline goldens against a real Kùzu database. Live-model validation runs nightly with a daily cap; credentials exist only in that job. The nightly live job is not yet implemented: no workflow runs it in 0.3.0, and [BUILD_PLAN.md](BUILD_PLAN.md) carries it (WP-3.11).

**D-25 · A change ships with the test that would have caught it.** Each pull request that closes an audit finding carries the regression test for it. Adapters are tested against fake CLI binaries on `PATH`. No package the CLI depends on may be without tests.

**D-26 · Pull requests are small and package-confined; integration is reviewed by the maintainer.** One PR per decision or audit item group, under roughly four hundred changed lines, rebased on `main` daily. Package-confined PRs may be merged by the implementing agent when CI is green and an independent verifier has passed them. PRs touching `run.ts`, `RoleDispatcher.ts`, `wiring.ts`, workflow files, or versions require the maintainer.

**D-27 · Agents stop and ask** before changing behaviour the README describes, adding a dependency, editing a workflow file, refactoring beyond the task, or crossing a phase boundary. Releases, tags, repository settings and visibility are the maintainer's.

## Added during Phase 1 integration (2026-10-08)

**D-28 · `git.reset` ends its argv with `--`, not `--end-of-options`.** Supersedes the second clause of D-12 for `reset` only. `git reset` accepts `--end-of-options` only from git 2.44; the trailing separator makes git read the checked revision as a revision on every supported git, and the revision pattern already refuses anything that starts with `-`.

**D-29 · The security diff is the whole repository minus this run's runtime state.** The reviewed diff is taken with the `:(top)` pathspec — the full tree, however deep inside the repository MAF was pointed — and excludes only the entries under `<cwd>/.maf/` that a run produces (the `.gitignore` "runtime state" list: `runs/`, `cache/`, `memory.kuzu`, `lcm.db*`, `transcripts/`, `attestations/`, `harnesses/`, `goldens/results/`, `evolve/`; 0.3.0 adds `approvals/`, the headless approval gate's pending records, written by MAF when nobody can answer). MAF's configuration under `.maf/` — `policy.yaml`, `roles.yaml`, `config.yaml`, `prompts/` — is content an agent could rewrite to shape the next run, and stays in the diff. Runtime state is excluded because it grows during the run, is written by MAF rather than the agent, and would push an honest diff past the gate's cap (D-07) in a repository that does not ignore it.

**D-30 · A tester may not write CI configuration.** Globs match dotfiles (D-08), so the tester's `**/*test*` allow-list reached `.github/workflows/test.yml`. The shipped policy denies the tester writes under `.github/` at a priority above its allow-list. A workflow file is CI configuration, not a test.

**D-31 · A backend that throws is reviewed before the failure propagates.** When the adapter or the in-process loop throws (a timed-out turn, a backend that never started), the dispatcher runs the security gate on whatever the agent left in the tree before rethrowing: a gate refusal (a verdict) outranks the transport failure; a clean or empty diff lets the original error through for the scheduler to classify (D-06). On the in-process tier the gate otherwise runs at `task_end`, which a throw never reaches.

**D-32 · A role says whether it is expected to change the tree.** A writer-role node on the `cli` tier can exit 0 with an answer and leave the tree untouched — a backend running under the user's own permission settings refuses the edit and says so — and D-04 reads that as a success. Each role now carries `expectsChange`; a node whose role expects a change and whose diff against the start commit is empty fails with `NodeFailure('no_change')`, the output tail in the error. In the built-in set only `coder` expects a change: `tester` holds `patch.apply` and legitimately changes nothing on most runs, and `security` and `reviewer` hold no write tool. A custom role declares its own expectation. Chosen over a blanket rule with a per-node opt-out (which would make the common tester run a failure to be waived) and over leaving the verdict as is with a `changed: false` beside it (which keeps `Succeeded` meaning two things). Ships in 0.3.0 (WP-2.1). The judgment applies on either tier; the in-process judgment lands in 0.3.0, found when WP-2.18 made a run of failed tool calls survivable.

## Added during Phase 2 integration (2026-10-09)

**D-33 · An in-process turn spawns its backend with native tools off.** The governed loop's only tools are MAF's. For Claude, `sendTurn` passes `--tools ""` beside the strict-MCP flags, in one documented constant; the cli tier keeps the backend's native tools and isolates only MCP. Codex has no known equivalent and keeps `inProcessLoop` off. Found by the WP-2.1 verifier: under D-01 every writer on Claude ran through `sendTurn`, whose `claude --print` still had Claude Code's own tools.

**D-34 · The review gate exists only when asked for.** `run` constructs it when the harness requires review or the operator passes `--review`; an advisory gate so constructed makes each writer node wait for the decision, bounded by the gate's timeout. A required review with no reviewer available (stdin not a TTY, or `MAF_HEADLESS=1`) refuses every writer change — fail closed. `--review` with no reviewer available prints one line and runs without a gate. Chosen over "advisory does not wait" (which needs a drain before the bundle that a forgotten call would silently skip) and over constructing a reviewer whenever stdin is a TTY (which would hold every default run on a human).

**D-35 · The worktree directory is not runtime state.** `MAF_RUNTIME_STATE` keeps D-29's list; `.maf/worktrees/` stays out of the parent's diff through its own `.gitignore`, so adding it to the list only widened the unreviewed set. A run branch that commits runtime state gets no merge command: `finish` refuses and names the paths.

**D-36 · The attestation signs RFC 8785 bytes.** A dedicated serializer in `@maf/attestation` (`jcs.ts`: keys sorted by UTF-16 code units, numbers per `Number::toString`, §3.2.2.2 escapes) produces the signed bytes and is what `maf attest verify` recomputes. `canonicalJson` in `@maf/types` keeps its 0.2.x behaviour (integer-like keys first, `__proto__` dropped) so no harness sha moves, and its comment says it is not RFC 8785. The approval gate hashes requests with its own stricter serializer (refuses NaN, undefined and Date), kept on purpose: a request hash must fail loudly on a value that cannot round-trip.

**D-37 · Failure recall keys on the run title.** Every planned node carries `metadata.runTitle`; the recorder stores it on the Task; recall matches the title's first three words, as one phrase and ignoring case, against the Task's label or properties with bound parameters. The recorder wait is bounded (10 s, unref'd) so a hung recorder cannot hold the run or the bundle.

**D-38 · `goldens compare` compares like with like.** Results that differ in adapter, model or attempt count are refused (exit 2); result files are validated on load and named `<harnessSha>.<adapter>.json`; a missing or malformed file exits 2, a rejection exits 1.

**D-39 · Reserved harness ids, honest CURRENT, safe writes.** `harness import` refuses `legacy-default`, `current` and `CURRENT`; `set-current` refuses a `legacy-default` snapshot that is not the newest mint (pin one with `--harness <sha>`); `adoptLegacy` rewrites nothing that already verifies and every store write goes through a temp file and `rename`, so a concurrent reader never sees a half-written harness.

**D-40 · A YAML merge key is refused.** `parseYamlDocument` (config and roles files) refuses a `<<` key at any depth, naming the file and line. YAML 1.2 has no merge; silently keeping `<<` as a literal key dropped the merged fields without a word. Write the keys out in full.

## Added during the 0.3.1 evidence work (2026-10-13)

**D-41 · A test runner that is not installed is a failed result, not a fatal spawn.** `test.run` spawns the runner with no shell, so an absent binary fails the spawn; `spawn` reports that with an `error` event, and an unhandled `error` on a `ChildProcess` kills the whole process. A live v0.3.0 run whose tester asked for `bun` died with `Error: spawn bun ENOENT` and wrote no attestation, which is WP-2.18's rule one level further out: a tool that fails while running answers with a result, and so does one that never started. The same run exposed the second half — `node` and `pnpm` sit in the schema's `enum`, so a model may ask for them, but neither had a `case` and both fell through to `npm test`. A model that asked for the one runner the `node:test` fixture wanted silently ran npm. Every advertised runner now has its own case, and a test empties `PATH` so an absent binary is reproducible on any machine rather than depending on which runners the host happens to have.

**D-42 · A role that holds no write tool is diffed, not trusted.** A node that holds no write tool — either tier — brackets its turn with two working-tree snapshots (`snapshotTree`, taken through the same throwaway index and pathspec as `snapshotDiff`) and diffs those (`diffTrees`); a writer still diffs against the commit it started from, as the gate has always done. A non-writer whose *turn* changed the tree fails with `unexpected_change`, the exact mirror of D-32's `no_change`, and the change is recorded as a subject of the run's attestation. The guard inherits the review diff's exclusions and no others — a path the repository's `.gitignore` already ignores, and this run's runtime state under `.maf/` (D-29), are outside it — and it can misattribute only a writer editing *concurrently* with the reader's turn, a window a `cli`-tier reader cannot enter because it holds the writer lock. The bracket, not a diff against the start commit, is what attributes the change to the node: a sibling writer that ran before it and committed nothing — no node commits between DAG nodes — leaves its work in the shared worktree, and under `--no-worktree` the tree may already be the user's own dirty checkout; both sit in the start snapshot and cancel out, so neither is the reader's to answer for. Diffing against `HEAD` instead would fail the reader for work it never did, the false positive this replaced. One case the bracket cannot separate — a writer editing the tree *concurrently* with the reader's turn — is documented in SECURITY.md: the scheduler serializes writers, so a plan's sequential `coder` → `reviewer` is exact, and the residual window can only misattribute a failure, never let a change pass unattested. Nothing is reverted: under the default run and under `--no-worktree` the tree is the user's own checkout, so the failure message names the files and prints the `git diff` / `git checkout --` lines. On the `claude` backend a `cli`-tier reader is additionally spawned with only the reading tools (`--tools Read,Glob,Grep`); `codex` and `gemini` have no known equivalent, and there the diff is the only guard, which the documentation states rather than implies. The node's tier and any D-06 fallback are recorded in the bundle's `executionTiers`, because on the `cli` tier the policy engine never sees a tool call, so a Deny rule scoped to a `cli`-tier role such as `reviewer` is in force and unreachable — and only the tier shows which node that rule failed to reach. The prompt files now say what is enforced ("a change you make fails this node") in place of a "No writes" instruction that no layer enforced. Found by an audit row: a read-only `reviewer`, Deny rule and all, edited a tracked file and the run recorded `Succeeded` with no subject, no diff and no finding.

## Added during the Phase 3 readers work (2026-10-14)

**D-43 · The `analyst` role: a fifth built-in, for a question rather than a diff.** A plan can ask the code a question — "list every TODO in `src/` and say which look stale" — and the four-role set had nowhere to route it. `security` audits a diff for CWE/OWASP classes and `reviewer` approves or rejects one; both answer "is this change safe / good", not "what does this code do". A planner with only those had to choose between a writer (`coder`, which would try to change the tree) and a reader whose prompt asks a different question. `analyst` holds `fs.read, fs.list, fs.stat, grep, git.status, git.diff, git.log` — the seven read tools, no write tool — so `isWriterRole(analyst)` is false and it is not reviewed; it carries no `expectsChange`, because answering a question changes nothing and a role that owes no change must not fail for making none (D-32). Its `description` is written for the planner — "Read-only. Answers a question about the code, investigates, reports. Makes no change." — and the planner's role block tags every role by what it does to the tree, from the role's `writes`/`expectsChange` and never its name, so a question routes here because the block says "read-only". The role catalogue entry gained those two booleans for that block (`packages/roles/src/RoleConfig.ts`); the planner's own catalogue type (`planning-agent`) gained the same. Ships in 0.4.0 (WP-3.0b).

**D-44 · The built-in readers run in-process.** `security`, `reviewer` and `analyst` carry `execution: 'in-process'`. On the `cli` tier a read-only role is handed the backend's own file tools — the allowlist is not passed to it (D-01) — so an audit or a review that only reads the tree is still a change MAF did not gate at the moment it happened; F7's `unexpected_change` guard catches it after the fact, but a guard is a fallback, not the first line. In-process is where the policy engine, secret redaction and attested tool calls exist, so running a reader there is what makes its reads governed rather than merely observed. D-01's default is unchanged for a role a user defines: a custom reader still runs on the `cli` tier unless it sets `execution: 'in-process'`, because a user's own role is theirs to place and the built-in set is MAF's to get right. Where the adapter cannot run the loop (`codex`, `gemini`, `ollama`, `openrouter`) the three readers fall back to `cli` with the D-06 note and a `fellBackFrom: 'in-process'` record in `executionTiers`, exactly as before, and a reader that changes the tree during that fallback still fails with `unexpected_change`. Until WP-3.0c's attribution lands, a built-in reader whose turn overlaps a writer can fail with `unexpected_change`; `wp/phase-3` is not promoted before 3.0c. Ships in 0.4.0 (WP-3.0b).

## Added during the WP-3.0c record work (2026-10-14)

**D-45 · Every role call is in the record: a model surface on both tiers, and the F7 window attributed rather than charged.** Two gaps about what a run's evidence holds once a role may run on the `cli` tier, closed together.

*The surface.* F4 recorded the model-facing surface (`systemPromptSha256`, `toolCatalog`, `argv`) for a governed in-process turn alone, because that is where MAF composes the system block and the tool catalogue; a `cli`-tier role call was unrecorded — MAF held neither what it handed the backend nor what came back. Now a `cli`-tier **role** call records one too. `AdapterInvokeResult` gains an optional `modelSurface`, which each CLI adapter fills from the argv it actually spawned with: `ClaudeAdapter` replaces the `--system-prompt` value and the prompt after `--`; `GeminiAdapter` replaces the `--system-instruction` value and the value half of the joined `--prompt=` token; `CodexAdapter` takes the prompt on stdin, so its argv is verbatim and only the digests record the text. `RoleDispatcher` records it through `attestor.recordModelSurface` and the transcript. Every surface now carries a `tier` of `in-process` or `cli`, so a reader can see which tier a call was made on; `promptSha256` and `outputSha256` are added and filled on the `cli` tier (absent on a governed turn, whose prompt is the serialized history the loop owns and whose answer is a parsed `AssistantTurn`, not one stdout string). `toolCatalog` stays required and is the empty string on the `cli` tier: MAF composes no catalogue there — `''` on this tier means **MAF composed no catalogue**, not that the backend had none; `nativeTools` says what the backend had — so the one record shape both tiers share states the absence rather than omitting the field. A cli-tier record also carries `nativeTools`, of `full` / `read-only` / `none`, which is what MAF **asked** of the backend's own tools rather than what the backend then did — the `claude` reader's `--tools Read,Glob,Grep` is `read-only`, a CLI writer that keeps its whole toolset is `full`. Only `claude`, `codex` and `gemini` fill a surface at all; `ollama` and `openrouter` spawn no process and compose no argv, so a role call routed to them is still not recorded, which SECURITY.md says outright rather than leaving the reader to infer from a claim about "the `cli` tier". The `tier` and the two new digests are optional in the type, so a 0.3.1 bundle — whose records carry neither — still parses and verifies. The planner's call and the security reviewer's call remain outside this record, because MAF spawns them itself rather than through a role node; that is stated in SECURITY.md rather than left implied.

*The window.* D-42's bracket attributes a reader's change by diffing two working-tree snapshots, which cancels out work present *before* the turn but cannot separate a *writer* editing the tree *during* it. The scheduler serializes writers (A3) and now keeps a **ledger** of hold intervals: `DagRunner` stamps a new `WriterLockLedger` (`createWriterLockLedger`, exported from `@maf/dag-runner`) where it takes and releases the writer lock, and `RoleDispatcher` asks it — for a reader whose bracket shows a diff — who held the lock across the reader's own turn. A writer answers for the turn only on evidence, and the reader's own node is never its own writer. Two conditions qualify a writer, tried in this order: the writer is a node this dispatcher started as a **writer** (`writerNodes` — a `cli`-tier reader holds the same lock but runs no gate, so naming it would excuse a change to a node that never judges it), it is **still holding** the lock at the reader's end snapshot, and its post-coder gate has **neither begun nor run** for this attempt (`writer && holding && !gating && !gated` — the `gating` marker is set before the gate's first read, so a change landing after that read is not named on the lock), so the gate it is about to run will read the change; or the writer is **gated** (its post-coder gate has run), **every path in the bracket diff is in the diff that writer reviewed** (`reviewedPaths`, filled by that writer's own post-coder gate), and those paths are **unchanged** between the tree that gate read and the reader's end tree — `git diff --no-renames <writerGateTree> <readerEndTree> -- <paths>` empty. Both path sets are taken from git — `git diff --name-only -z --no-renames` between the bracket's two trees, and between the writer's start commit and its gate tree — never by parsing `---`/`+++` lines out of a diff, which git does not emit for a non-ASCII path (C-quoted), a mode-only change (no file lines), or a pure rename (collapsed header), so a parsed set could silently omit a path the diff changed and excuse it. When a writer qualifies, the node does **not** fail: `{nodeId, attributedTo, diffSha256, fromTree, toTree, writerGateTree?}` is recorded in a new optional `attributedChanges` bundle field (`Attestor.recordAttribution`) and in the transcript, and the change is judged where every writer's change is judged — against that writer's own start commit, by the security gate that reviews it. Any change the rule cannot settle is the reader's: the node fails with `unexpected_change` and the diff is recorded as the reader's own — a writer that overlapped but reviewed nothing, or that is neither still-holding-ungated nor gated-and-accountable, excuses nothing. The bracket diff is itself a subject of the run's statement, under `<node>.attributed.diff`, and `diffSha256` is reproducible from the recorded ids: `GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_NOSYSTEM=1 git diff --text --no-ext-diff --no-textconv --no-renames <fromTree> <toTree>` in the run's repository prints exactly the bytes the digest is over. Those are the flags the digest was taken with — without `--text` a binary change prints `Binary files … differ` and the bytes come out different — and because maf runs git with the host's global and system config off, a verifier's own `diff.*` settings must be off too; the two tree objects are unreachable in that repository, so `git gc` may prune them once `gc.pruneExpire` passes (two weeks by default): recompute soon after the run, or pin the ids under a ref. On the `cli` tier the ledger is not consulted at all (F4): a `cli`-tier reader holds the writer lock itself (the scheduler serializes every `cli`-tier role), so no other writer can have been running and any change the bracket shows is its own; the `exclude` parameter an earlier draft needed, and the wall-clock comparison it rested on, are gone. `wiring.ts` builds no ledger at all: its dispatcher runs a single node with no scheduler behind it, so `attributableWriter` returns nothing and its readers fail closed — the pre-3.0c behaviour, unchanged and unreachable for a concurrent writer. This reverses the clause of D-42 that reads "the residual window can only misattribute a failure, never let a change pass unattested": the window no longer fails a reader for a change its writer took to that writer's own gate. It strengthens rather than weakens the half it keeps — after F2 a change passes unattested only when **no** writer's reviewed diff holds it and **no** writer still holds the lock, which is exactly the change D-42 means to fail. The "until WP-3.0c's attribution lands" clause in D-44 is discharged — the built-in readers no longer fail for a concurrent writer's change — and with it D-44's promotion gate: `wp/phase-3` may be promoted once this work is merged and the WP-3.0c live rows have run, exactly as 3.0b's gate closed on its merge plus its rows. Ships in 0.4.0 (WP-3.0c).

## Added during the WP-3.1 no-work work (2026-10-14)

**D-46 · The governed turn says what it has, and a reader that did no work has not succeeded.** Two findings from the 0.3.0 sweep's F12 (`claims-vs-record`) — L2 (MED) and L3 (LOW) — closed together; both change behaviour, so both ship in 0.4.0.

*What the turn has (L2).* The governed in-process loop's `TOOL_PROTOCOL` block now opens by telling the model that the host's own tools are not available in this turn and that a request for one is refused: *"The host's own tools — Read, Write, Edit, Bash, Glob, Grep, WebFetch, or any other tool you may believe you have — are not available in this turn, and a request for one is refused. The only tools you have are the ones listed below; request one with a fenced block exactly as described, by its id."* Before this the block described how to request a MAF tool and never said the backend's own tools were gone, so a model could answer by asking for `Read`/`Bash`/a tool it believed it had — a request the loop had no way to honour. This is the prompt half of D-33, which spawns the backend with its native tools off (`claude` `--tools ""`); the prompt and the spawn now agree. `TOOL_PROTOCOL` is not part of `HarnessConfig` — the value `computeHarnessSha` hashes — so no committed harness moves for this half.

*A reader that did no work (L2).* A **non-writer** node on the **in-process** tier that finishes with an answer after **zero executed tool calls** now fails with `no_work`, rather than succeeding on an answer the model produced without looking at anything. "Executed" is `policyDecision.verdict === 'Allow'` alone: a call the policy engine denied — and, for an `Escalate`, that the approval gate then refused — did not run, and is not work. The message names the role, the number of turns, and the first 200 characters of the final output with newlines collapsed, and carries the F10 deny clause (`; N tool call(s) were denied or refused by policy: …`) when the node's own calls were refused. The check is scoped to the in-process tier, where a per-call `ToolCallRecord` exists: the `cli` tier attests no per-call record for a role call, so a check there would fire on every `cli`-tier reader — live row 1 among them — and is not made. A role opts out with `RoleConfig.expectsToolCalls: false`; absent, a non-writer that lists at least one tool is expected to call one, and a role that lists none is not (`expectsToolCalls(role) = role.expectsToolCalls ?? role.allowedTools.length > 0`). No built-in sets it, so the three built-in readers keep `true`, and `RoleCatalogEntry` does not change — the planner's role block still routes by what a role does to the tree, not by whether it calls a tool. A test double that answers no `toolCallsForTask` reads as zero executed calls and so fails **closed**, which is deliberate: production's `RoleDispatcherConfig.attestor` is the `Attestor` class, which always answers it, and the alternative — treating an absent getter as "unwatched, skip the check" — would silently disable the guard for the one caller that forgot to implement it.

*The refusal in the outcome (L3).* `RunOutcome.nodes[].failure` is a value, not only a sentence: `{ kind, ruleId?, toolId? }`, where `kind` is the `NodeFailureReason` the dispatcher decided — the tree's existing name for what the spec called `NodeFailureKind`; no synonym was minted — and `ruleId`/`toolId` name what a policy refusal named. `NodeFailure` carries the two ids (optional, so a failure with no refusal reads as exactly `{ kind: 'no_work' }` rather than a record salted with `undefined`), and `DagRunner` fills `failure` from it when a node fails. A plain `Error` — a transport or programming failure with no verdict — leaves `failure` absent rather than inventing a kind. The field is optional, so a bundle and a baseline that predate it still parse.

Ships in 0.4.0 (WP-3.1).
