# WP-3.15 — one default role set (D-61), and `maf init` records its harness (S6)

Branch: `wp/3.15-roles` → `wp/phase-3b`

## What this changes

There were two default role sets, maintained by hand beside each other: the built-in
`DEFAULT_ROLE_SET` in `packages/roles/src/defaults.ts`, and the `.maf/roles.yaml` plus prompt files
the package ships (byte for byte as this repository's `.maf/` holds them, kept identical by
`packages/cli/src/__tests__/assets.test.ts`). They had drifted: the built-in tester held no
`fs.write` while the shipped one did (F2), and the prompts differed. Which set a run used depended
on whether the target directory had a roles file, so the same task ran different roles in two
directories with no visible reason.

**One source now.** `.maf/roles.yaml` and the prompt files it names are the definition. A generated
module, `packages/roles/src/defaultRoleSet.generated.ts`, is their compiled form — each role's
prompt *text* inlined (not its path, which a target without `.maf/prompts/` could not read), plus
every field the file declares: `policyTag`, `model`, `execution`, `expectsChange`,
`expectsToolCalls`, `timeouts`, limits and the allowed tools. `DEFAULT_ROLE_SET` re-exports it;
`defaults.ts` no longer writes a role.

`scripts/generate-default-roles.mjs` renders the module from `.maf/roles.yaml` and its prompts and
is runnable two ways:

```
node scripts/generate-default-roles.mjs           # rewrite the generated module
node scripts/generate-default-roles.mjs --check   # exit 1 when it is out of date
```

### The drift tests

`packages/roles/src/__tests__/one-role-set.test.ts` holds the two sides together. It loads
`.maf/roles.yaml` through the same `RoleRegistry` a run uses and compares, role by role and field
by field, the built-in set against it: the default role, the roles and their order, every field, the
tool set, and each built-in prompt against the text of the file it names. It also runs the
generator's `--check` as a test, so editing `.maf/roles.yaml` or a prompt without regenerating
fails the suite, and asserts that the built-in set carries no `promptFile` — a target with no
`.maf/prompts/` runs it.

`role-name-mint.test.ts` gains the generated file as a role-set author: it mints names, as
`defaults.ts` used to, but every name it mints is one the roles file declared.

### A real defect the move surfaced

Retargeting the R13 test ("a prompt's tool line names exactly what its role may call") to the
shipped syntax — the readers' prompts say `You may use:`; the built-in prompts used to say `Tools
available:` — found that all three shipped reader prompts omitted `lcm.expand` while their
`allowedTools` granted it. A reader was handed a Dolt cue it could follow and a prompt telling it it
could not. The tool is added to the `You may use:` line of `security`, `reviewer` and `analyst` in
`.maf/prompts/` and in `packages/cli/assets/prompts/` (both copies move together). The F7 closing
sentence is checked in the shipped wording, which names the `unexpected_change` failure the guard
produces.

## S6 — `maf init` records the harness, and `show current` answers

- **`maf init` writes `CURRENT`.** After copying the shipped files, `runInit` imports the default
  harness it installed into the store (`.maf/harnesses/<sha>.yaml` plus `index.json`) and points
  `CURRENT` at it, printing
  `[maf] init: CURRENT → default (<sha>), the default harness it installed`. It reads the package's
  copy, which is the same bytes it wrote, so a skipped or hand-edited destination cannot change what
  is recorded. An **existing `CURRENT` is the operator's and is left alone, with or without
  `--force`** — `--force` replaces the files `init` ships, not the pointer the operator chose.
- **`maf harness show current` with no `CURRENT` names the harness a plain run uses** instead of
  failing with `No harness found for ref "current"`: `legacy-default`, minted in memory from
  `.maf/roles.yaml` as it is now, or from the built-in set when there is no file (D-08). One note
  goes to stderr (`[maf] no CURRENT in <dir>: a plain run uses legacy-default (<sha>) — …`) and the
  harness JSON goes to stdout, so a script reading it is unaffected. Nothing is written: asking what
  would run does not change it.
- **The F2 notice changed with the fact it reported.** `run` printed
  `using the built-in role set (maf init writes the shipped one)` to warn that the two sets
  differed. Since D-61 they are one set; the line now reads
  `using the built-in role set (the same one maf init writes)` and is still printed only when the
  roles file is absent (`packages/cli/src/commands/run.ts`, the `harnessSource === 'legacy'`
  branch; test updated in `cli/run-d49-policy.test.ts`).

### Consequence for an operator, stated

After `maf init`, `CURRENT` names the installed default, so **a plain run dispatches that harness
(`[current]`) rather than minting `legacy-default` from `roles.yaml` (`[legacy]`)**. Editing
`.maf/roles.yaml` or its prompts no longer changes a plain run by itself — the harness was hashed
when it shipped. To hand plain runs back to the roles file, run `maf harness set-current
legacy-default` (which is also what the error messages already name). `--harness <id|sha|prefix>`
still pins one harness for one run. This is the point of recording the harness — a fresh
repository runs the harness the release was tested with — but it is a behavior change, not only a
bookkeeping one.

## D-61 — One default role set

The built-in role set is the shipped `.maf/roles.yaml` and prompts, compiled in: one source
(`.maf/roles.yaml` + `.maf/prompts/*.md`, written by `maf init` from `packages/cli/assets/`), the
other generated from it (`scripts/generate-default-roles.mjs` → `defaultRoleSet.generated.ts`) with a
drift test that fails when either moves alone. The built-in set carries prompt text, never a
`promptFile`: it must run in a target with no `.maf/prompts/`. A field added to a role is hashed by
the generator without an edit there, but is dispatched only once `roleConfigFromHarness` carries it
too — the two directions of `harnessBridge.ts` remain a pair.
